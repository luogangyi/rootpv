# Ascend 950DT 计算与 RootPV 复测（2026-11-12）

**按厂商方案配置 `udma` 并重启后，普通 Pod 与 RootPV 的实际 NPU 计算及本记录中的生命周期用例通过。**
本轮没有修改 RootPV Go 代码，也没有增加仓库测试代码；复用已有在线验证脚本。
[前次记录](ascend-950-2026-11-11.md) 保留设备初始化失败和驱动重装未解决故障的证据。

## 环境与修复

| 项目 | 本次组合 |
| --- | --- |
| 平台 | Linux ARM64；企业 Linux 25.0.2（厂商构建）；kernel 6.6；cgroup v1 |
| 集群 | Kubernetes 1.34.3（厂商构建）；containerd 2.3.5；磁盘配置 version 3；overlayfs |
| NPU | 8 个 Ascend950DT 资源，非切分模式；资源键 `huawei.com/npu` |
| 驱动 / 固件 | 25.1.rc3.1 / 9.2.0.101.235 |
| runtime / plugin | Ascend Docker Runtime 26.1.0 / device plugin 26.1.0；底层 runc 1.1.13 |
| plugin 镜像 | `ascendai/ascend-k8sdeviceplugin:v26.1.0-openeuler24.03`，ARM64 |
| 应用镜像 | `ascendai/cann:9.1.0-950-ubuntu22.04-py3.11`，ARM64 |
| UMDK | 宿主 25.12.0-B129；plugin/CANN 镜像 26.06.0-B016；本轮均未更换 |
| 存储 | 两个静态 local PV，XFS `ftype=1`，Filesystem/ReadWriteOnce，Retain；未使用动态/云盘卷 |
| RootPV | `ascend` 分支 ARM64 构建；真实 Controller、Webhook/catalog、node-agent 和 wrapper |

厂商通过环境使用方提供以下配置。备份模块配置、启动标识和集群状态，确认 NPU 无计算进程，
暂停节点调度后写入 `/etc/modprobe.d/udma.conf` 并重启：

```text
options udma dfx_switch=1 fast_destroy_tp=0 jfc_arm_mode=2
```

- 新 boot ID 确认节点已重启；`dfx_switch` 从 `N` 变为 `Y`，`jfc_arm_mode` 从 `0` 变为 `2`。
- 当前模块不支持 `fast_destroy_tp`，内核记录 `unknown parameter 'fast_destroy_tp' ignored`。
  保留厂商原文，不声称该参数生效；本轮未隔离测试其余单个参数的作用。
- 驱动、固件、CANN、UMDK 版本及原厂 Ascend handler 均未改变。此前同版本驱动重装加重启仍失败，
  本次配置生效后的对照通过；不再把 UMDK 版本差异本身视为该故障的已证实原因。
- 恢复节点调度及原有独立 registry 容器，containerd、kubelet、监控、device plugin 和 RootPV 组件均正常。

该配置是本环境的厂商修复方案，不是全部 950/UMDK 版本的通用要求，RootPV 不自动修改它。

## 复测结果

计算使用 CANN `aclnnAdd`，逐元素校验 256 个 float32：`out[i] = 5*i + 2`，总和 `163712`。
普通 Pod 和 RootPV 使用相同镜像与计算程序，没有通过特权、host PID/IPC/network 绕过故障。

| 用例 | 结果 |
| --- | --- |
| 普通 Pod 全设备实算 | 一次申请 8 个资源，逐个逻辑设备的初始化、算子、数据回传和数值校验全部通过 |
| 普通 Pod 小规模对照 | 分别申请 2 个和 1 个资源，全部实算通过；未手工指定物理设备 ID |
| 宿主对照 | 只读挂载同一镜像的 CANN，使用宿主驱动/UMDK；初始化、设备数量 8、setDevice/reset/finalize 全部成功，随后卸载临时挂载 |
| Webhook 与原厂委托 | 源 `ascend` 自动转换为 `persistent-rootfs-ascend`；生成 runc-v2 shadow handler，OCI 保留原厂 prestart hook |
| RootPV 三代持久化 | 前两代分配 2 个资源，第三代分配 1 个；每代实算通过，marker 不变，计数 1→2→3 |
| sidecar 隔离 | 每代没有 app marker、NPU 计算/管理设备；临时根目录全新，`ASCEND_VISIBLE_DEVICES=void` |
| rootfsd 重启 | app 保持运行，重启后重新实算通过，marker 与计数保持 |
| containerd 重启 | app/sidecar 保持运行，重启后重新实算通过，后续删除/重建正常 |
| 单写互斥 | 同一路径竞争者被阻止，原 writer 锁仍持有且实算通过；删除双方后竞争者成功接管，计数递增、实算通过 |
| catalog 自恢复 | 删除测试 catalog ConfigMap 与 Ascend shadow RuntimeClass 后自动重建；server dry-run 正确转换；无可用 adapter 的源 RuntimeClass 被 RootPV Webhook 拒绝 |
| 公开 YAML | 仅替换节点和专用 PV 目录；在原有四代数据上继续第 5、6 代，marker 不变，计数递增，单 NPU 实算与 sidecar 检查均通过 |
| 删除清理 | 测试 Pod/sandbox/shim、RootPV runtime state 和相关 overlay 挂载均为 0；四个写层租约 released，文件锁可重新获取 |

公开 YAML：[ascend-950.yaml](../manifests/ascend-950.yaml)。其 readiness 只验证设备和文件，
上表实际计算通过来自额外执行的算子程序，不能把 Pod Ready 等同于计算验收。

## 最终状态与边界

- 节点 Ready，资源容量 8，NPU 无计算进程；原默认 runtime 保持 `runc`，源 Ascend handler 内容不变。
- 节点重启造成平台容器重启；恢复后 11 个平台 Pod 的 UID 和重启次数在复测期间保持。
  metrics-server 从启动后的未就绪变为就绪，未发生额外重启。全部平台 Pod 最终就绪。
- 保留厂商 `udma` 配置、Ascend runtime/plugin、隔离 RootPV 部署和 PV/PVC 数据供后续使用。
  删除测试业务 Pod 和临时拒绝路径 RuntimeClass；Webhook 仍只匹配专用 namespace 标签。
- 这次验证重启完成后的计算、服务重启后的新算子执行和根文件系统持久化；
  **不覆盖在途 NPU 任务/显存状态恢复**，也不覆盖其他 950 型号、驱动升级、vNPU/共享/CDI、HCCL、
  多机计算、动态 CSI、异常断电或性能。
- 公开记录不包含主机名、地址、凭据、私有镜像源、Pod UID 或具体设备分配 ID；原始证据保留在私有目录。
- 文档相对链接、YAML 结构、容器 shell 语法、环境信息脱敏检查及 `git diff --check` 通过。
