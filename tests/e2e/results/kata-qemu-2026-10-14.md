# Kata + QEMU 功能验证

- 日期：2026-10-14。
- 分支：lgy/kata-qemu。
- 环境：隔离测试环境 的 Linux AMD64 裸金属 worker。
- Kubernetes：v1.34.3（厂商构建）；containerd：2.1.1。
- Kata：4.2.0 Rust runtime；QEMU：11.0.1 (kata-static)，KVM；guest kernel：6.18.35。
- 原 RuntimeClass/handler：kata-qemu；源 runtime_type：io.containerd.kata-qemu.v2。
- 存储：专用 local PV、ReadWriteOnce PVC，宿主机 ext4（独立块设备）；storageClassName=rootpv-local。
- 镜像：测试节点已缓存的 nginx:1.21.4。
- 部署：单节点隔离 RootPV 实例；webhook 仅匹配本次测试 namespace。使用交叉编译的 Linux 二进制及已有基础镜像运行，未执行容器镜像构建/推送。

## 已通过

| 检查 | 结果 |
| --- | --- |
| 自动发现 imports 中的 Kata handler | catalog、节点 registry、就绪标签及 Shadow handler 自动生成 |
| 保留原 runtime 选择 | 启用 RootPV 后映射为 persistent-rootfs-kata-qemu，adapter 为 kata-qemu-v2 |
| RuntimeClass 约束 | 保留原节点调度条件，overhead 为 CPU 250m、内存 160Mi；增加 adapter 就绪标签 |
| 多容器与真实 VM | app 和 sidecar 均 Ready，exec 读到 guest kernel 6.18.35 |
| 写层真实性 | app 写入 /rootpv-kata.marker；宿主机 PVC upper 中可读取同一内容 |
| 重建持久化 | 三轮 Pod 创建、两次复用同一写层，标记从 kata-qemu-first 更新为 kata-qemu-second 并再次读回 |
| 文件操作 | rename 后内容保留，权限 0640 和符号链接在重建后保留 |
| sidecar 隔离 | 不读取 app 标记；sidecar 自己的根目录标记在重建后消失 |
| 单写者互斥 | 并发 Pod 的目标容器创建被 rootfsd 以 409 Conflict / persistent_upper_in_use 拒绝；原 app 标记完整 |
| rootfsd 重启 | 节点 agent 重启后恢复持有的租约，运行中的 Kata app 仍可读写；之后正常删除并释放租约 |
| 普通 Kata Pod | 未启用 RootPV 的 Pod 保持 runtimeClassName=kata-qemu，没有 adapter annotation，正常启动 |
| 正常删除 | 先完成 Kata task 删除，再卸载 merged；state.json 消失，lease.json 的 phase 为 released |
| 清理与还原 | 测试 namespace、PV/PVC、停止的 sandbox、测试 shim、RootPV 控制面与节点文件均清理；原 containerd 配置按字节恢复 |
| 原有负载 | 测试前的所有 Running Pod 的 UID、phase、各容器 ready 和 restartCount 均未改变；测试 worker 最终 Ready |

测试二进制、配置副本和已释放租约的数据移入节点专用备份目录。原 Kata/QEMU 安装及原 RuntimeClass 保留。
清理过程按测试 namespace 的日志核实 sandbox ID 和进程 starttime，没有按任意 Kata binary 路径批量终止业务进程。
