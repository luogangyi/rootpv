# 官方 CRI-O + runc 功能验证与 containerd 回归

日期：2026-11-16。对应 `crio` 分支；记录仅包含本轮实际执行项。
环境名称、地址、节点名、私有仓库、PVC ID、访问凭据及原始日志均不进入此记录。

## 范围与构建

本分支仅接入未修改的官方 CRI-O + conmon + runc，不依赖 CRI-O 或 runtime 上游补丁。
原 CRI-O + Kata/gVisor 实验、诊断补丁及历史证据保存在独立
[`cri-o-with-kata-and-gvisor` 分支](https://gitcode.com/luogangyi/rootpv/tree/cri-o-with-kata-and-gvisor)。

| 项目 | 本轮基线 |
| --- | --- |
| 平台 | Linux AMD64、5.10 内核、Kubernetes 1.37.1 |
| CRI-O | 官方 1.37.3；源码标识 `e2f2af62b2574a33ea864f918326efbfc24b7303`；运行进程指向官方发行包二进制 |
| OCI | 官方 runc 1.5.2、conmon；显式 OCI handler |
| 存储 | rootful containers/storage overlay；ext4 local PV；串行动态 EBS |
| 安全前提 | `internal_wipe=false`、`internal_repair=false`；无 SELinux mount label/userns |
| RootPV | 当前源码交叉构建 AMD64 controller/agent/wrapper/helper，挂载到隔离测试部署；完整 Docker 镜像另行构建验证 |
| 备份 | 变更前保存 Kubernetes 资源、runtime/service/kubelet/RootPV 配置、二进制及挂载状态；两种 CRI 的存储目录分别保留 |

测试开始前停用并备份旧诊断配置，移走旧 VM handler/drop-in/registry，再激活本分支。
全部下表 CRI-O 用例均在官方 1.37.3 上重新执行，未沿用旧诊断版的通过结果。

## CRI-O + runc

| 用例 | 实际结果 |
| --- | --- |
| 原生基线 | 16 项检查通过：双容器 Ready、exec/logs、跨节点 IPv4/IPv6、双栈 Service、DNS、普通 PVC 顺序重建 |
| 在线控制链 | 真实 Webhook 注入、inventory/catalog/shadow、显式与默认 runtime 路由通过；opt-out 保留原 RuntimeClass |

| 持久化与隔离 | 删除重建后标记、0640 权限、硬链接/符号链接和 whiteout 保留；未选 sidecar 重置；新工作目录和 projected token 可用 |
| 多容器与单写 | 两个选定容器使用独立 path 重建通过；相同 PVC/path 的第二写者收到 `persistent_upper_in_use` |
| 并发隔离与强删 | 3 个独立 local PVC 并发运行并顺序重建，身份标记互不混淆；强制删除后同 path 可复用 |
| Strict | 不同镜像链收到 `base_image_mismatch`，未静默接纳 |

| 服务恢复 | 分别重启 rootfsd 和官方 CRI-O，随后再次触发应用退出/重启，数据保留且可删除 |
| 失败回滚 | 直接调用不存在的程序触发 CreateContainerError；删除失败 Pod 后，同路径可重新使用 |
| EBS | 同一动态 PVC 顺序创建、删除、重建；第二代只校验既有标记；最后删除 PVC 并等待 PV 回收，无并发 EBS 创建 |
| 镜像引用 GC | 使用当前 helper 实现创建独立测试镜像引用；原容器记录删除后，引用仍阻止 DeleteImage；释放引用后该测试镜像可回收，原镜像未改变 |
| handler 退休 | 源 handler 移除后撤销 readiness，拒绝新 create；既有容器可 exec/delete，退休入口仍可响应版本探测；不支持的 crun 不影响 runc |

临时验证脚本的 namespace 标签覆盖、helper 交叉编译架构和 BusyBox 文件系统名称输出断言

## containerd 回归

回归使用同一候选 RootPV 构建和原有官方 containerd；Kata proxy 源码与主线一致。
仅在专用节点受控切换 CRI，并在切换前排空 RootPV；未覆盖或替换任一 runtime 的数据 store。
回归基线为 containerd 2.1.1；Kata 4.2.0 Rust + QEMU 11.0.1；gVisor release-20261012.0。
Kata 原生和 RootPV Pod 均出现初始 DNS 尚未收敛的短暂超时，随后有界重试通过；
该现象未通过改动 RootPV 或上游 runtime 代码规避。
三个 runtime 各完成以下 7 组检查，共 21 组通过：

1. 原生 Pod 的启动、exec/logs 和 DNS。
2. 真实 Webhook 路由、所选容器根目录、sidecar 隔离、工作目录与 projected token。
3. 同 Pod 应用退出重启，计数与数据连续。
4. rootfsd 重启后再触发应用退出，恢复与数据正确。
5. containerd 服务重启后再触发应用退出，恢复与数据正确。
6. 删除重建后标记、权限、硬链接/符号链接、whiteout 保留，sidecar 内容重置。
7. 删除后 runtime state 清理完成。

回归期间 CRI stats 查询成功。最终审计确认无测试容器、runtime state、RootPV 挂载、
QEMU/Kata shim/runsc shim/runsc 进程残留。随后恢复官方 CRI-O 1.37.3 + runc，
再次通过真实 Webhook、CRI stats、持久化重建与全部清理检查。containerd 配置恢复到切换前备份，
服务恢复停用；保留隔离的 CRI-O + runc 测试部署和既有 local PVC 数据，不恢复此前已停用的 VM 工作负载。

## 本地检查与限制

- 主模块现有 Go 测试、Linux 测试及 `go vet` 通过。
- 独立 storage helper 的现有测试通过；AMD64 完整 Docker 镜像构建通过。
- Helm lint、默认 containerd 和 CRI-O values 渲染通过。
- 本轮仅增加一个短的 CRI-O 非 runc handler 拒绝单测；在线驱动和原始环境证据不提交仓库。
- GPU/NPU 环境不存在，未执行 NVIDIA/Ascend 设备分配、计算、MIG/vNPU 回归；既有 containerd 硬件结果仍只对应其原记录。
- 不覆盖其他 CRI-O/runc 版本、SELinux、userns、跨 CRI 持久化层迁移、runtime 版本升级/回滚、性能或长时间压力。
- 本轮功能验证不等于兼容性规划中所有版本/架构/升级组合均已通过。
