# Ascend 950DT 部分验证记录（2026-11-11）

> 后续进展：按厂商方案配置 `udma` 并重启后，计算阻塞已解除，见 [2026-11-12 复测记录](ascend-950-2026-11-12.md)。以下保留当时的失败与排障事实。

**RootPV 的设备注入与根文件系统生命周期通过；实际 NPU 计算未通过。**
普通 Ascend Pod、RootPV Pod 和宿主直接加载 CANN 库均在 `aclrtSetDevice(0)` 返回 `507033`。
因此本记录不作为 950 完整计算兼容性的通过证明。

## 环境与接入

| 项目 | 本次组合 |
| --- | --- |
| 平台 | Linux ARM64；企业 Linux 25.0.2（厂商构建）；kernel 6.6 |
| 集群 | Kubernetes 1.34.3（厂商构建）；containerd 2.3.5；磁盘配置 version 3；overlayfs；cgroup v1 |
| NPU | 8 个 Ascend950DT 资源，非切分模式；device plugin 公布 `huawei.com/npu` |
| 驱动 / 固件 | 25.1.rc3.1 / 9.2.0.101.235 |
| 原厂组件 | Ascend Docker Runtime 26.1.0；device plugin 26.1.0；底层 runc 1.1.13 |
| plugin 镜像 | `ascendai/ascend-k8sdeviceplugin:v26.1.0-openeuler24.03`，ARM64，含 UMDK |
| 应用镜像 | `ascendai/cann:9.1.0-950-ubuntu22.04-py3.11`，ARM64，含 950 算子包和 UMDK |
| UMDK | 宿主 25.12.0-B129；上述 plugin/CANN 镜像内为 26.06.0-B016；版本配套尚未完成计算验收 |
| 存储 | 两个独立静态 local PV，XFS `ftype=1`，Filesystem/ReadWriteOnce，Retain；未使用动态/云盘卷 |
| RootPV | `ascend` 分支 ARM64 构建；当前 Helm Chart，真实 Controller、Webhook/catalog、node-agent 和 wrapper |

现有通用 runc-v2 adapter 能委托 950 原厂 runtime；本轮没有增加厂商专用 Go 分支或单元测试。
安装原厂组件时备份 containerd 配置，另行导入 `ascend` handler，绝对 `BinaryName` 指向原厂 runtime，
默认 runtime 保持 `runc`。RootPV 生成 `persistent-rootfs-ascend-runc-v2`，registry 保留原厂委托路径。
containerd dump 输出 version 4，但本次磁盘配置为 version 3，不据此声称 version 4 自动发现已验证。

初次使用 Ubuntu 22.04 plugin 镜像时缺少 `liburma.so.0`，导致 DCMI 初始化失败；
改用含 UMDK 的官方 openEuler 镜像后，资源注册为 `huawei.com/npu: 8`。
按实际 socket 路径分别配置 device-plugin 和 pod-resources 挂载；不能仅按自定义 kubelet 根目录推导二者。
plugin 使用源 `ascend` RuntimeClass，保留官方清单中的 `MOUNT_BY_RUNTIME_FOR_DP=true`。
26.1.0 不以旧版 `ASCEND_DOCKER_RUNTIME=True` 环境标记作为验收要求。

## 实际计算阻塞与对照

计划使用 CANN `aclnnAdd`，逐元素校验 `out[i] = 5*i + 2`（256 个 float32 元素，预期总和 163712）。
本次在设置第一个逻辑设备时失败，尚未执行到算子，不能将设备数量查询或 `npu-smi` 正常当作计算成功。

- 普通 Pod：设备分配正常，`aclrtSetDevice(0)` 返回 507033；近期错误为 E39006。
- 原厂 HDC 日志：发送 `Ascend-aicpu_legacy.tar.gz` 至设备失败，`drvHdcSendFile` 返回 96；
  底层记录 `hdc_poll_jfc`/`service_file_trans` 异常，设备侧 `hdcd` 记录会话失效。
- 临时 hostNetwork Pod、特权 Pod，以及 host PID/IPC/network 加无限 memlock 的组合均未消除故障，诊断 Pod 已删除。
- 在普通 Pod 中仅替换为宿主 UMDK 库的对照仍失败；该次库对照未修改宿主组件，后续同版本驱动重装见下节。
- 将同一 CANN 镜像只读挂载到宿主，使用宿主 Python、设备和驱动/UMDK 库直接调用，仍返回 507033；随后卸载临时挂载。
- 原厂 `msnpureport` 能导出设备日志，NPU 健康显示 OK、设备 0 当前故障事件为 0；这些管理查询不证明计算通路正常。

这些对照证明失败不依赖 RootPV 或 Kubernetes 容器；尚不能确定是 CANN/HDK/UMDK 配套问题还是设备侧通信缺陷。
下一步需要用该环境已知可工作的镜像/版本组合复测，或结合原始 Host/Device HDC 日志完成原厂定位。
解决普通 Pod 计算后，再完整重跑 RootPV 实算及重建/重启后的计算用例；当前不通过扩大应用权限绕过此门槛。

## 同版本驱动重装与节点重启复测

按用户授权使用节点已有的 `Ascend-hdk-950-npu-driver_25.1.rc3.1_linux-aarch64.run`。
包内校验和、安装器的驱动/固件配套检查通过。备份驱动目录和配置，停止 NPU plugin/监控并暂停节点调度，
按原 `full`、root 用户、install-for-all 模式强制重装。DKMS 针对当前 Linux 6.6 内核重新编译成功，
安装器输出安装成功、需重启，退出码为 2。随后完成节点重启，以新 boot ID 确认生效；固件未重装。

- 恢复 device plugin 原 nodeSelector、监控服务和节点调度。8 个 NPU 健康、资源注册正常，RootPV Controller/DaemonSet 就绪。
- 原有独立 registry 容器未自动启动，已恢复该原容器；未另建替代服务。
- 普通 Pod 请求 8 个资源，设备数量查询通过；实际计算仍在 `aclrtSetDevice(0)` 返回 507033。
  宿主 CANN 对照也重现 HDC 文件发送返回 96，重装与重启没有消除该故障。
- 在新的专用 rootfs 路径重跑三代持久化、设备注入、sidecar、单写互斥和 rootfsd/containerd 重启，均通过；实际计算仍单列为阻塞。
- 重启前公开 YAML 的 PVC 数据保留，继续创建第 3、4 代 Pod，marker 与重启前一致；计算仍失败。
- 业务测试 Pod 清理完成，三个写层租约释放；原 11 个平台 Pod 的 UID 保持，重启次数随维护增加，均恢复就绪；其后复测期间 UID、phase、就绪和重启次数无新增变化。

这次覆盖停载节点重启后的文件保留、服务恢复和重新创建容器，没有覆盖在途 NPU 计算恢复或异常断电。
